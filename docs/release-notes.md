## pydantic-zarr 0.11.0 (2026-10-31)

### Features

- Added support for the v2 chunk key encoding (`{"name": "v2", "configuration": {"separator": ...}}`) in the experimental `pydantic_zarr.experimental.v3` module, so experimental `ArraySpec` can model and round-trip Zarr v3 arrays that use it. ([#166](https://github.com/zarr-developers/pydantic-zarr/issues/166))
- `pydantic_zarr.v3.ArraySpec` now validates its fields as a whole Zarr V3 array metadata document, via the new `zarr-metadata` dependency: the fill value is judged against the data type, the chunk grid against the shape, and the codecs as a pipeline (a sharding codec's inner and index codecs too), each extension point by the definition that claims its name in a scope. A name nothing in the scope claims passes unjudged, so unknown extensions still work. The scope comes from the pydantic validation context (a `ZarrV3Context`, directly or under `pydantic_zarr.v3.CONTEXT_KEY`), defaulting to `zarr-metadata`'s `CORE_AND_EXTENSIONS`. With no `include`/`exclude` filters, `ArraySpec.like` now compares the two metadata documents by meaning rather than spelling (so a fill value written `"NaN"` equals one written `"0x7fc00000"`), with attributes still compared as plain fields. Non-finite float fill values are canonicalized to the string forms the spec requires (`"NaN"`, `"Infinity"`, `"-Infinity"`), and `parse_dtype_v3` and `from_array` handle `bool`, `datetime64` and `timedelta64` data types, emitting the named-configuration form for the time dtypes. `GroupSpec` member names are validated against the Zarr V3 node-name rules (via `validate_node_name_v3`): besides the previously rejected empty string, `"/"`, `"."` and `".."`, a name composed of periods alone or starting with the reserved `"__"` prefix is now refused. Member-name validation runs as a model validator rather than field metadata, so a subclass that narrows the `members` annotation — for example to a closed `TypedDict` of members, which pydantic enforces, making the shape of a hierarchy a statically and runtime-checked contract — keeps the node-name rules (the same holds for the v2 member-name check). This is breaking for specs that were constructible before but describe invalid metadata documents (for example an integer array with fill value `"NaN"`, a chunk shape whose rank disagrees with the shape, or a codec pipeline without an array -> bytes codec): constructing them now raises a `ValidationError` listing every problem. The Zarr V3 structural metadata types are now imported from `zarr-metadata` instead of being defined locally: `RegularChunking`/`RegularChunkingConfig`, `DefaultChunkKeyEncoding`/`V2ChunkKeyEncoding` and their configs are aliases of the `zarr-metadata` types, the chunk key encoding field accepts the spec's string short-hand (`"default"`/`"v2"`) and configuration-less object forms, `FillValue` is the JSON value type (per-data-type validity is judged by the document validator), and the v2 module's `DimensionSeparator`/`MemoryOrder` alias the `zarr-metadata` literals. The aliased TypedDicts are closed: unknown members are rejected instead of silently dropped. Property-based tests (hypothesis) check the validation by agreement with zarr-python: documents generated by zarr-python's own strategies are accepted and round-trip, documents from an independent generator dump to metadata zarr-python parses, single invalidating mutations are refused, and NaN fill-value spellings compare alike.
   With no `include`/`exclude` filters, `GroupSpec.like` now compares each member by that member's own `like`, so member arrays compare by the meaning of their metadata documents at any depth, in agreement with `ArraySpec.like`. The `include`/`exclude` filters of every `like` method are now keyword-only, matching the v3 `ArraySpec.like` signature.
   Three conveniences the first round of real-world modeling (OME-Zarr 0.5/0.6, GeoZarr Sentinel-2, xarray datasets) showed every user hand-rolling: `ArraySpec.from_shape_and_data_type(shape, data_type, **overrides)` builds a valid array spec from a shape and data type alone — its overrides are the same typed field set `update` accepts (minus the two positional arguments), and every absent field gets a spec default or one derived from the data type (guessed chunks, chunk key encoding, fill value, codecs); `GroupSpec.resolve_path(path)` (also spelled `group[path]`) resolves `/`-separated relative member paths, raising `KeyError` naming the failing segment; and specs serialize attribute models with `by_alias=True` by default, so attribute keys that are not Python identifiers (`_FillValue`, `image-label`, `proj:code`) are stored under their spec spelling instead of silently under Python field names. A new `pydantic_zarr.core.AttributesBase` base class for attribute models adds alias round-tripping and preservation of unknown keys; its optional keys are declared with pydantic's `MISSING` sentinel (re-exported as `pydantic_zarr.core.MISSING`, which resolves to the stable spelling on pydantic >= 2.14 and the experimental one on 2.12/2.13), so a field left at `MISSING` stays out of the serialized document and `null` is representable exactly where an annotation admits `None`. The `bytes` codec's no-op `endian` configuration is dropped at validation for single-byte data types, matching zarr-python's stored spelling, so either spelling round-trips equal through a store. pydantic >= 2.12 is now required (for the `MISSING` sentinel).
   Refinements from the second round of modeling: `from_shape_and_data_type` guesses a size-appropriate chunk shape (zarr-python's heuristic, now exported as `pydantic_zarr.core.guess_chunks`) instead of defaulting to one whole-array chunk; `GroupSpec.get_path(path, default=None)` is the non-raising counterpart of `resolve_path` (whose missing-member error now lists the available names) for use inside pydantic validators; and `pydantic_zarr.core.get_attribute` reads one key from attributes in either form a spec may hold (mapping or model, aliases and extra fields included).
   Following a comparison with zarrs' `ArrayBuilder`: the derivation table extends to the variable-length data types (`string` -> `vlen-utf8` codec with the empty-string fill, `bytes` and zarr-python's provisional `variable_length_bytes` spelling -> `vlen-bytes`), an empty codec `configuration` mapping is canonicalized away at validation (zarr-python writes the empty mapping, so round trips now compare equal for variable-length arrays too), and `ArraySpec.with_sharding_codec(subchunk_shape, index_location=...)` shards a spec the way zarrs' `subchunk_shape` does: the chunk shape becomes the shard shape and the existing codec pipeline moves inside the shards, with divisibility judged by document validation.
   `parse_dtype_v3` parses numpy data type declarations only: a declaration already in Zarr V3 form passes through unchanged, judged against the definitions in scope with the rest of the document — except that a string naming no data type in the scope that numpy would read as one (`"i8"`, `"float"`, `">f4"`) is refused as ambiguous, with the Zarr V3 spelling suggested where one exists; the spellings zarr-python has stored for the variable-length data types (`"str"`, `"variable_length_bytes"`) are recognized, so documents zarr-python wrote pass through. The refusal now runs on every spec construction, where previously only `from_shape_and_data_type` applied it.
   The validation scope can be a property of the model class, not only of each call: a subclass that sets the `zarr_scope` class variable (declared on `NodeSpec`, so `ArraySpec` and the group classes all carry it) validates in that scope whenever the validation context carries none — at direct construction and through every derived operation (`update`, `from_shape_and_data_type`, `like`), which re-validate as the class, so the scope choice sticks to the data instead of lasting one `model_validate(..., context=...)` call. An explicit validation context still wins, and the default remains `CORE_AND_EXTENSIONS`; a group's members are validated as their own classes, so a scoped tree narrows its member types to scope-bearing classes. A class that also sets `zarr_scope_strict` refuses the extension-point names the scope would leave unjudged (data type, chunk grid, chunk key encoding, codecs — a sharding codec's inner and index pipelines included — and storage transformers), turning the class into a conformance contract: `zarr_scope = CORE` plus strict accepts exactly the documents built from names the core spec defines. ([#183](https://github.com/zarr-developers/pydantic-zarr/issues/183))
- The generic type parameters of `ArraySpec` and `GroupSpec` (v2 and v3) now carry defaults (PEP 696), so the bare class names are fully usable without parametrization, while `ArraySpec[MyAttrs]` and subclass-level field narrowing keep working. `BaseGroupSpec` — a model of a group's own metadata, without members — is promoted from the experimental module to `pydantic_zarr.v2` and `pydantic_zarr.v3`: `to_flat` now emits it for every group (breaking: flat groups were previously `GroupSpec` instances with `members=None`), `from_flat` accepts it alongside the existing forms, and group `like()` comparisons against a `BaseGroupSpec` compare the group's own metadata. New `TypeIs`-based narrowing helpers (`is_array_spec`, `is_group_spec`, `is_base_group_spec` in both format modules) tell flattened-hierarchy values apart with full static narrowing, and the `GroupSpec` methods that override `BaseGroupSpec` are marked `@override`. ([#185](https://github.com/zarr-developers/pydantic-zarr/issues/185))
- `ArraySpec`, `BaseGroupSpec` and `GroupSpec` (v2 and v3) gain a typed `update(**changes)` method: it returns a revalidated copy with the changes applied in one validation pass, so correlated fields (a new `data_type` with a matching `fill_value`, a new `shape` with a matching `chunk_grid`) change together atomically — which per-field builders cannot express — and, unlike `model_copy(update=...)`, the result is always validated. The keyword arguments are statically typed via `Unpack` of per-model `*Update` TypedDicts. This replaces the (never-released) `with_*` builder methods. ([#186](https://github.com/zarr-developers/pydantic-zarr/issues/186))
- The spec type parameters (`TAttr`, `TItem`) are now covariant, in v2 and v3: the specs are frozen, so both parameters appear only in read positions on instances, and a narrowed spec is substitutable for a wider one. The `Any*` aliases (`AnyArraySpec`, `AnyGroupSpec`, `AnyBaseGroupSpec`) become ordinary wide types (`ArraySpec[TBaseAttr]` and friends) instead of gradual-typing escapes, so attributes and members read through them — including the results of `resolve_path`, `from_flat` and the `is_*_spec` guards — keep checked types instead of `Any`; code that leaned on those reads being `Any` may need narrowing. The constructing classmethods (`from_array`) take `attributes: TBaseAttr` instead of `TAttr`, since a covariant parameter may not appear in argument positions: the argument is checked against the class's attribute type by validation rather than statically, which is the trade that keeps `Self` return types for subclasses. ([#191](https://github.com/zarr-developers/pydantic-zarr/issues/191))
- Specs now accept the extra metadata fields the Zarr specs permit, instead of refusing every key they do not declare. A v3 array or group document may hold an extra field a definition in the validation scope claims, judged by that definition (`CORE` claims a group's `consolidated_metadata`, so documents zarr-python consolidated now validate), or an unrecognized extension object (a `name`, an optional `configuration`, no other members) that sets `"must_understand": false`, per the spec's rule that a reader must refuse a field it does not recognize unless the field says so; any other unknown key, a misspelled field name included, is still refused. A class with `zarr_scope_strict` set also refuses extra fields its scope does not claim. A v3 group now validates its extra fields as a whole document via `zarr-metadata`'s `ZarrV3GroupMetadata.from_json`. A v2 array accepts any other key (they "SHOULD be ignored"), and v2 groups still refuse them ("MUST NOT be present"). Accepted extra fields are kept in a new `extra_fields` field on v3 specs and on the v2 `ArraySpec`, written back as top-level members by `model_dump` and `model_dump_json`, kept through `update` (where `extra_fields=` replaces them), `like`, `to_flat` and `from_flat`, and on v3 written by `to_zarr` and read by `from_zarr` (arrays from zarr-python 3.1, groups from 3.4). `consolidated_metadata` is kept as written, not read as members: `from_zarr` leaves it out and `to_zarr` refuses a group holding it. ([#194](https://github.com/zarr-developers/pydantic-zarr/issues/194))
- `ArraySpec`, `BaseGroupSpec` and `GroupSpec` (v2 and v3) gain a `to_metadata_json()` method that returns the node's metadata document, statically typed with the `zarr-metadata` document types: `ZarrV3ArrayMetadataJSON` / `ZarrV3GroupMetadataJSON` for v3, and the merged `ZarrV2ArrayMetadataJSON` / `ZarrV2GroupMetadataJSON` (the `.zarray` / `.zgroup` fields plus `attributes` from `.zattrs`) for v2. Unlike `model_dump`, it takes no options, so its return type is exact. Extra fields (such as `consolidated_metadata`) are written as top-level members, and a group's `members`, which are not part of its metadata document, are left out. ([#195](https://github.com/zarr-developers/pydantic-zarr/issues/195))
- `pydantic_zarr.v2.ArraySpec` now validates its fields as a whole Zarr V2 array metadata document, via `zarr-metadata`'s `ZarrV2ArrayMetadata`, as the v3 `ArraySpec` does. This is breaking for specs that were constructible before but describe invalid `.zarray` documents (for example an integer array with fill value `1.5` or `"NaN"`, or a bool array with fill value `3`): constructing them now raises a `ValidationError` listing every problem. A spec built without a fill value, or by `from_array` from an array with no `fill_value`, now gets the default for its dtype: `0` when the dtype accepts `0` and `None` otherwise (bool, complex, string and structured dtypes), the rule `zarr-metadata` uses. The default was previously `0` for every dtype. The new `pydantic_zarr.v2.dtype_default_fill_value` returns it. A subclass that declares its own `fill_value` default keeps it. `update(dtype=...)` keeps the current fill value rather than re-deriving it, so changing to a dtype that refuses that value (an `int32` array with fill value `0` updated to a bool dtype, say) now needs a matching `fill_value` in the same call. ([#198](https://github.com/zarr-developers/pydantic-zarr/issues/198))
- `ArraySpec`, `BaseGroupSpec` and `GroupSpec` (v2 and v3) gain `to_stored_metadata_json()`, which returns the node's metadata as a Zarr store holds it: a mapping from each store key to the JSON document stored there, statically typed per key. For v3 that is `zarr.json`; for v2, `.zarray` or `.zgroup` plus `.zattrs`, written even when the attributes are empty, as zarr-python writes it. A `GroupSpec`'s mapping also holds every member's documents at any depth, at keys prefixed by the member's path (`"a/zarr.json"`, `"a/b/.zarray"`): the metadata documents `to_zarr` writes, so a consumer can write a hierarchy's metadata without zarr-python. The new classmethod `from_stored_metadata_json()` reads such a mapping back, with no store involved. The return types are `ZarrV3ArrayStoredJSON` / `ZarrV3GroupStoredJSON` and `ZarrV2ArrayStoredJSON` / `ZarrV2GroupStoredJSON`. ([#199](https://github.com/zarr-developers/pydantic-zarr/issues/199))

### Bugfixes

- Fixed unreachable match arms in `parse_dtype_v3` (in both `pydantic_zarr.v3` and `pydantic_zarr.experimental.v3`) where copy-paste errors caused `float64` and `complex64` numpy dtypes to raise `ValueError: Unsupported dtype` instead of returning the correct string names. ([#167](https://github.com/zarr-developers/pydantic-zarr/issues/167))
- Fixed `NameError` raised by `ArraySpec.like` and the module-level `from_zarr` in
  `pydantic_zarr.v3` and `pydantic_zarr.experimental.v3` when `zarr` was not explicitly
  imported before calling these functions (zarr was only imported under `TYPE_CHECKING`).
  Also fixed a `KeyError` raised by `ArraySpec.model_dump(exclude={'dimension_names'})` in
  both modules. ([#169](https://github.com/zarr-developers/pydantic-zarr/issues/169))
- Fixed `model_like` and `BaseModel.like` reporting a spurious mismatch when two specs have JSON-identical attributes that differ only by lists versus tuples (for example a freshly built spec compared against the same spec read back from storage, where `from_zarr` converts attribute lists to tuples). Comparison now uses a recursive, list/tuple-insensitive equality check (`json_eq`). ([#170](https://github.com/zarr-developers/pydantic-zarr/issues/170))
- Fixed test-suite collection (`Struct`/`Structured` dtype) and mypy type-checking under zarr-python 3.2.x. ([#171](https://github.com/zarr-developers/pydantic-zarr/issues/171))
- Fixed array creation failing under zarr-python 3.3+ with `ValueError: The 'endian' configuration needs to be specified for multi-byte data types.` The `auto_codecs` functions in `pydantic_zarr.v3` and `pydantic_zarr.experimental.v3` (used by `ArraySpec.from_array` when `codecs="auto"`) now emit `{"name": "bytes", "configuration": {"endian": "little"}}` for multi-byte data types, matching zarr-python's default, instead of an endian-less `bytes` codec. Explicitly declared endian-less `bytes` codecs are passed through unchanged, so materializing them with a multi-byte data type still raises zarr's error. Also added zarr-python 3.3.0 to the test matrix. ([#172](https://github.com/zarr-developers/pydantic-zarr/issues/172))
- Fixed the `@overload` signatures of `pydantic_zarr.v2.from_zarr` and `pydantic_zarr.experimental.v2.from_zarr`, which declared `depth` without a default and so rejected the documented single-argument call `from_zarr(group)` under a type checker.

  Widened `pydantic_zarr.experimental.v2.GroupSpec.from_flat` to accept `Mapping[str, ArraySpec | BaseGroupSpec]`, matching what `GroupSpec.to_flat` returns and what the module-level `from_flat` already accepted. Round-tripping `GroupSpec.from_flat(group.to_flat())` previously failed to type-check. ([#181](https://github.com/zarr-developers/pydantic-zarr/issues/181))
- Fixed `pydantic_zarr.v3.ArraySpec.from_array` raising `ValueError` for every `bool` array: `auto_fill_value` tested the dtype character `"?"` where numpy reports the *kind* `"b"`, so the bool branch was unreachable. `from_array` also no longer emits invalid data type names for non-core numpy dtypes (such as `"datetime64[ns]"`), since the data type is now derived via `parse_dtype_v3` instead of `str(array.dtype)`.
   `ArraySpec.from_array` given a `zarr.Array` now reads the array's whole stored metadata document (via `from_zarr`) instead of probing attribute names that `zarr.Array` does not have, which silently produced a chunk grid equal to the array's shape and dropped the chunk key encoding and the attributes; explicit (non-`"auto"`) keyword arguments still override the stored values, and a Zarr V2 `zarr.Array` is refused. Metadata documents without the `attributes` key, which the Zarr V3 spec makes optional, are now accepted: `attributes` defaults to the empty dict on every node class (v2 and v3), with the default validated against the model's attributes type, so a model whose attributes type does not accept the empty dict still requires explicit attributes.
   `dimension_names` is now omitted from the serialization of arrays nested as members in a group's dump (and from JSON serialization) when it is `None`, as it already was at the top level: the omission moved from a `model_dump` override, which pydantic does not call for nested models, to a model serializer.
   Review findings addressed: comparing a `GroupSpec` to a `BaseGroupSpec` with `like` now works as documented, by the group's own metadata alone, at any depth — the comparison previously always failed at the top level because only one side was reduced to its own metadata (while a `GroupSpec` with unknown members, the shape a depth-limited `from_zarr` leaves at its cutoff, is alike the same or a projection, never a group with known members); the single-byte `bytes`-codec normalization reaches inside a sharding codec's inner pipeline (index codecs keep their endianness); and `from_shape` no longer mistakes a Zarr V3 data type name that numpy parses as something else (the variable-length `"bytes"` type) for a numpy equivalent.
   A single codec passed where a codec pipeline is expected is now refused with a message saying to wrap it in a sequence; iterating the lone mapping or string previously validated its keys or characters as (unclaimed, so silently accepted) codec names. A numpy-style data type string that is not a Zarr V3 name (`"i8"`) is refused by `from_shape_and_data_type` with a message suggesting the V3 spelling. ([#183](https://github.com/zarr-developers/pydantic-zarr/issues/183))
- Fixed group member type parameters refusing narrowed specs under strict type checkers: `GroupSpec[Attrs, MyArraySpec]` — a group parameterized with a narrowed member spec — is accepted by mypy and pyright, where the `TItem` bound previously resolved through its PEP 696 defaults to invariant `TBaseAttr` specializations that refuse narrowed specs. The spec type parameters are covariant, which is what makes the narrowed parameterizations ordinary subtypes. ([#190](https://github.com/zarr-developers/pydantic-zarr/issues/190))
- `pydantic_zarr.v2.ArraySpec` now holds its fill value in the Zarr V2 JSON form, as the v3 spec already did. Non-finite floats become the strings `"NaN"`, `"Infinity"` and `"-Infinity"`, so `json.dumps` of `model_dump()` no longer writes a bare `NaN` that strict JSON parsers reject. Numpy scalars become Python scalars: an `np.int16` fill value was previously stored as a float, and the imaginary part of an `np.complex64` was dropped. Complex numbers (Python or numpy) become `(real, imaginary)` pairs, in both the v2 and v3 specs. `canonicalize_fill_value` moves to `pydantic_zarr.core` and is still importable from `pydantic_zarr.v3`. ([#198](https://github.com/zarr-developers/pydantic-zarr/issues/198))
- Stopped `AttributesBase` and the experimental v3 `ArraySpec` and `GroupSpec` from passing an `extra` setting to the TypedDicts they hold. Building a model whose attributes nest a closed TypedDict no longer emits pydantic's `TypedDictExtraConfigWarning`, and each nested TypedDict now keeps or drops unknown keys as it would under any other model. `AttributesBase` keeps the keys it does not declare apart from its fields, read through a read-only `extra_fields` mapping: a frozen attributes model hashes by its declared fields, an attribute named `extra_fields` round-trips like any other key, and a subclass that sets `extra="allow"` is refused. ([#200](https://github.com/zarr-developers/pydantic-zarr/issues/200))

### Improved Documentation

- Corrected docstring examples in `v2.py` and `v3.py` (and experimental equivalents): fixed copy-pasted v2 output in a v3 example, missing commas, wrong import aliases, a `zarr_format=2` in a v3 example, "codices" → "codecs", "Compare am" → "Compare an", and a truncated sentence in the `to_zarr` docstring. Also fixed `V2ChunkKeyEncoding` to reference the correct config TypedDict, and modernized lint: `for` loops instead of list-comprehension side effects, `dict(data)` instead of `dict(data).copy()`, single-item `in` tests to equality, and raw strings in `pytest.raises(match=…)` calls. ([#168](https://github.com/zarr-developers/pydantic-zarr/issues/168))
- Four worked examples join the documentation, one per real-world layout the API was exercised against: OME-Zarr 0.5 and 0.6 images, a GeoZarr Sentinel-2 product, and xarray-style datasets. Each shows the typed-attributes and typed-members patterns (closed `TypedDict` member sets, `AttributesBase` attribute models, `from_shape_and_data_type`, `resolve_path`/`get_path`, cross-member validators), round-trips its hierarchy through a store, and demonstrates the refusals the model enforces; each example is a self-contained, executable script under `examples/` (PEP 723 metadata included, so `uv run examples/<name>.py` works standalone) whose sections the documentation pages embed, executed whole by the documentation test suite — and each script proves its model by writing the hierarchy and comparing every stored metadata document, exactly, against what a reference implementation writes (xarray for the dataset layouts, `ome-zarr-py` for OME-Zarr 0.5, `ngff-zarr` for OME-Zarr 0.6).
   The Zarr V3 usage page gains a section on validation scopes: how the metadata document check judges each extension-point name by the definition that claims it, choosing the scope per call through the validation context, making it a property of the model with the `zarr_scope` class variable, and strict conformance with `zarr_scope_strict`, with executable examples for each. ([#183](https://github.com/zarr-developers/pydantic-zarr/issues/183))
- The documentation gains a contributing guide covering tool setup, the just task recipes, towncrier fragment conventions, and the dependency and lockfile policy, linked from a new Development section in the README; packaging metadata gains the `Typing :: Typed` classifier and a Changelog URL. ([#188](https://github.com/zarr-developers/pydantic-zarr/issues/188))

### Deprecations and Removals

- `GroupSpec.members` in `pydantic_zarr.v2` and `pydantic_zarr.v3` is no longer nullable, and a `GroupSpec` is now always a complete hierarchy. `members` is a mapping of `ArraySpec` and `GroupSpec` values that still defaults to `{}`, so an empty mapping always means "no members". `BaseGroupSpec` is no longer accepted as a member. A group whose members are unknown is a `BaseGroupSpec`, which only appears on its own or in a flat hierarchy. `GroupSpec.from_zarr` and the module-level `from_zarr` lose their `depth` parameter and always read the whole hierarchy. The new `from_zarr_flat(node, depth=n)` reads part of a hierarchy into the flat form that `to_flat` produces and `from_flat` takes. To migrate, replace `GroupSpec(members=None, ...)` with `BaseGroupSpec(...)`, including in the flat mappings passed to `from_flat`. Replace `GroupSpec.from_zarr(group, depth=0)` with `BaseGroupSpec.from_zarr(group)`, and other `depth` reads with `from_zarr_flat(group, depth=n)`. ([#192](https://github.com/zarr-developers/pydantic-zarr/issues/192))
- The members an experimental v3 `ArraySpec` or `GroupSpec` does not declare are no longer pydantic extras. Read them from the read-only `spec.extra_fields` mapping (or `get_attribute(spec, "key")`) instead of `spec.key` or `spec.model_extra`. They still dump back as top-level members, a dump's `include` and `exclude` still name them by key, and `model_copy(update=...)` still sets them. A plain TypedDict held by an experimental v3 spec now drops unknown keys, as it does under any other model; declare it with `extra_items=` (PEP 728) to keep them. The experimental v3 metadata objects (`NamedConfig` and the chunk grid and chunk key encoding configurations) declare `extra_items=object`, so they still keep members such as `must_understand`. The experimental v3 module no longer defines `StrictBase`, and a subclass of its `NodeSpec` that sets `extra="allow"` is refused. ([#200](https://github.com/zarr-developers/pydantic-zarr/issues/200))

- Add `with_*` methods to the experimental `ArraySpec` and `GroupSpec` classes.
  These methods make it easier to create copies of existing `ArraySpec` and `GroupSpec` objects with
  new properties. ([#137](https://github.com/zarr-developers/pydantic-zarr/issues/137))

### Bugfixes

- Make V3 `ArraySpec` validation reject dimension names that don't match the dimensionality of the array. ([#136](https://github.com/zarr-developers/pydantic-zarr/issues/136))
- Fix a bug that prevented creation of `experimental.v3.GroupSpec` instances with typed members. ([#138](https://github.com/zarr-developers/pydantic-zarr/issues/138))
- Fix a bug where `experimental.v3.ArraySpec` instances took a default parameter for attributes. ([#138](https://github.com/zarr-developers/pydantic-zarr/issues/138))


## pydantic-zarr 0.9.0 (2025-12-08)

### Breaking Changes

This release contains breaking changes. See [Bugfixes](#090-bugfixes)

### Features

- Make the zarr dependency optional to allow usage without installing zarr-python. ([#112](https://github.com/zarr-developers/pydantic-zarr/issues/112))
- Add experimental module with improved implementations of `ArraySpec` and `GroupSpec` classes. ([#120](https://github.com/zarr-developers/pydantic-zarr/issues/120))

### Bugfixes<a id='090-bugfixes'></a>

- Remove default empty dictionary for attributes in ArraySpec and GroupSpec. This is a breaking change.
To migrate your code, provide a value for the `attributes` argument when creating an `ArraySpec` or
`GroupSpec`. ([#115](https://github.com/zarr-developers/pydantic-zarr/issues/115)).
To replicate the previous default behaviour, pass an empty dictionary (`attributes={}`).
- Fix a broken bare install by making the dependency on `packaging` explicit. ([#125](https://github.com/zarr-developers/pydantic-zarr/issues/125))

### Improved Documentation

- Update documentation URLs to point to pydantic-zarr.readthedocs.io. ([#123](https://github.com/zarr-developers/pydantic-zarr/issues/123))
- Add `towncrier` for managing the changelog. ([#128](https://github.com/zarr-developers/pydantic-zarr/issues/128))

### Misc

- [#121](https://github.com/zarr-developers/pydantic-zarr/issues/121)
