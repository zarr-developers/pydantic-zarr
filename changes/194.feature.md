Specs now accept the extra metadata fields the Zarr specs permit, instead of refusing every key they do not declare. A v3 array or group document may hold an extra field a definition in the validation scope claims, judged by that definition (`CORE` claims a group's `consolidated_metadata`, so documents zarr-python consolidated now validate), or an unrecognized extension object (a `name`, an optional `configuration`, no other members) that sets `"must_understand": false`, per the spec's rule that a reader must refuse a field it does not recognize unless the field says so; any other unknown key, a misspelled field name included, is still refused. A class with `zarr_scope_strict` set also refuses extra fields its scope does not claim. A v3 group now validates its extra fields as a whole document via `zarr-metadata`'s `ZarrV3GroupMetadata.from_json`. A v2 array accepts any other key (they "SHOULD be ignored"), and v2 groups still refuse them ("MUST NOT be present"). Accepted extra fields are kept in a new `extra_fields` field on v3 specs and on the v2 `ArraySpec`, written back as top-level members by `model_dump` and `model_dump_json`, kept through `update` (where `extra_fields=` replaces them), `like`, `to_flat` and `from_flat`, and on v3 written by `to_zarr` and read by `from_zarr` (arrays from zarr-python 3.1, groups from 3.4). `consolidated_metadata` is kept as written, not read as members: `from_zarr` leaves it out and `to_zarr` refuses a group holding it.
