Fixed `pydantic_zarr.v3.ArraySpec.from_array` raising `ValueError` for every `bool` array: `auto_fill_value` tested the dtype character `"?"` where numpy reports the *kind* `"b"`, so the bool branch was unreachable. `from_array` also no longer emits invalid data type names for non-core numpy dtypes (such as `"datetime64[ns]"`), since the data type is now derived via `parse_dtype_v3` instead of `str(array.dtype)`.
 `ArraySpec.from_array` given a `zarr.Array` now reads the array's whole stored metadata document (via `from_zarr`) instead of probing attribute names that `zarr.Array` does not have, which silently produced a chunk grid equal to the array's shape and dropped the chunk key encoding and the attributes; explicit (non-`"auto"`) keyword arguments still override the stored values, and a Zarr V2 `zarr.Array` is refused. Metadata documents without the `attributes` key, which the Zarr V3 spec makes optional, are now accepted: `attributes` defaults to the empty dict on every node class (v2 and v3), with the default validated against the model's attributes type, so a model whose attributes type does not accept the empty dict still requires explicit attributes.
 `dimension_names` is now omitted from the serialization of arrays nested as members in a group's dump (and from JSON serialization) when it is `None`, as it already was at the top level: the omission moved from a `model_dump` override, which pydantic does not call for nested models, to a model serializer.
 Review findings addressed: comparing a `GroupSpec` to a `BaseGroupSpec` with `like` now works as documented, by the group's own metadata alone, at any depth — the comparison previously always failed at the top level because only one side was reduced to its own metadata (while a `GroupSpec` with unknown members, the shape a depth-limited `from_zarr` leaves at its cutoff, is alike the same or a projection, never a group with known members); the single-byte `bytes`-codec normalization reaches inside a sharding codec's inner pipeline (index codecs keep their endianness); and `from_shape` no longer mistakes a Zarr V3 data type name that numpy parses as something else (the variable-length `"bytes"` type) for a numpy equivalent.
 A single codec passed where a codec pipeline is expected is now refused with a message saying to wrap it in a sequence; iterating the lone mapping or string previously validated its keys or characters as (unclaimed, so silently accepted) codec names. A numpy-style data type string that is not a Zarr V3 name (`"i8"`) fails default derivation with a message suggesting the V3 spelling.
