`pydantic_zarr.v3.ArraySpec` now validates its fields as a whole Zarr V3 array metadata document, via the new `zarr-metadata` dependency: the fill value is judged against the data type, the chunk grid against the shape, and the codecs as a pipeline (a sharding codec's inner and index codecs too), each extension point by the definition that claims its name in a scope. A name nothing in the scope claims passes unjudged, so unknown extensions still work. The scope comes from the pydantic validation context (a `ZarrV3Context`, directly or under `pydantic_zarr.v3.CONTEXT_KEY`), defaulting to `zarr-metadata`'s `CORE_AND_EXTENSIONS`. With no `include`/`exclude` filters, `ArraySpec.like` now compares the two metadata documents by meaning rather than spelling (so a fill value written `"NaN"` equals one written `"0x7fc00000"`), with attributes still compared as plain fields. Non-finite float fill values are canonicalized to the string forms the spec requires (`"NaN"`, `"Infinity"`, `"-Infinity"`), and `parse_dtype_v3` and `from_array` handle `bool`, `datetime64` and `timedelta64` data types, emitting the named-configuration form for the time dtypes. `GroupSpec` member names are validated against the Zarr V3 node-name rules (via `validate_node_name_v3`): besides the previously rejected empty string, `"/"`, `"."` and `".."`, a name composed of periods alone or starting with the reserved `"__"` prefix is now refused. Member-name validation runs as a model validator rather than field metadata, so a subclass that narrows the `members` annotation — for example to a closed `TypedDict` of members, which pydantic enforces, making the shape of a hierarchy a statically and runtime-checked contract — keeps the node-name rules (the same holds for the v2 member-name check). This is breaking for specs that were constructible before but describe invalid metadata documents (for example an integer array with fill value `"NaN"`, a chunk shape whose rank disagrees with the shape, or a codec pipeline without an array -> bytes codec): constructing them now raises a `ValidationError` listing every problem. The Zarr V3 structural metadata types are now imported from `zarr-metadata` instead of being defined locally: `RegularChunking`/`RegularChunkingConfig`, `DefaultChunkKeyEncoding`/`V2ChunkKeyEncoding` and their configs are aliases of the `zarr-metadata` types, the chunk key encoding field accepts the spec's string short-hand (`"default"`/`"v2"`) and configuration-less object forms, `FillValue` is the JSON value type (per-data-type validity is judged by the document validator), and the v2 module's `DimensionSeparator`/`MemoryOrder` alias the `zarr-metadata` literals. The aliased TypedDicts are closed: unknown members are rejected instead of silently dropped. Property-based tests (hypothesis) check the validation by agreement with zarr-python: documents generated by zarr-python's own strategies are accepted and round-trip, documents from an independent generator dump to metadata zarr-python parses, single invalidating mutations are refused, and NaN fill-value spellings compare alike.
 With no `include`/`exclude` filters, `GroupSpec.like` now compares each member by that member's own `like`, so member arrays compare by the meaning of their metadata documents at any depth, in agreement with `ArraySpec.like`. The `include`/`exclude` filters of every `like` method are now keyword-only, matching the v3 `ArraySpec.like` signature.
 Three conveniences the first round of real-world modeling (OME-Zarr 0.5/0.6, GeoZarr Sentinel-2, xarray datasets) showed every user hand-rolling: `ArraySpec.from_shape_and_data_type(shape, data_type, **overrides)` builds a valid array spec from a shape and data type alone — its overrides are the same typed field set `update` accepts (minus the two positional arguments), and every absent field gets a spec default or one derived from the data type (guessed chunks, chunk key encoding, fill value, codecs); `GroupSpec.resolve_path(path)` (also spelled `group[path]`) resolves `/`-separated relative member paths, raising `KeyError` naming the failing segment; and specs serialize attribute models with `by_alias=True` by default, so attribute keys that are not Python identifiers (`_FillValue`, `image-label`, `proj:code`) are stored under their spec spelling instead of silently under Python field names. A new `pydantic_zarr.core.AttributesBase` base class for attribute models adds alias round-tripping, preservation of unknown keys, and omission of unset `None` fields (an explicitly set `None` is kept). The `bytes` codec's no-op `endian` configuration is dropped at validation for single-byte data types, matching zarr-python's stored spelling, so either spelling round-trips equal through a store. pydantic >= 2.11 is now required.
 Refinements from the second round of modeling: `from_shape` guesses a size-appropriate chunk shape (zarr-python's heuristic, now exported as `pydantic_zarr.core.guess_chunks`) instead of defaulting to one whole-array chunk, and accepts a plain mapping for `attributes`; `GroupSpec.get_path(path, default=None)` is the non-raising counterpart of `resolve_path` (whose missing-member error now lists the available names) for use inside pydantic validators; `AttributesBase` gains a class-level `explicit_none` policy (`"keep"`, `"omit"`, or `"refuse"`) governing explicitly assigned `None`s; and `pydantic_zarr.core.get_attribute` reads one key from attributes in either form a spec may hold (mapping or model, aliases and extra fields included).
