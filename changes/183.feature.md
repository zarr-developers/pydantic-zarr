`pydantic_zarr.v3.ArraySpec` now validates its fields as a whole Zarr V3 array metadata document, via the new `zarr-metadata` dependency: the fill value is judged against the data type, the chunk grid against the shape, and the codecs as a pipeline (a sharding codec's inner and index codecs too), each extension point by the definition that claims its name in a scope. A name nothing in the scope claims passes unjudged, so unknown extensions still work. The scope comes from the pydantic validation context (a `ZarrV3Context`, directly or under `pydantic_zarr.v3.CONTEXT_KEY`), defaulting to `zarr-metadata`'s `CORE_AND_EXTENSIONS`. With no `include`/`exclude` filters, `ArraySpec.like` now compares the two metadata documents by meaning rather than spelling (so a fill value written `"NaN"` equals one written `"0x7fc00000"`), with attributes still compared as plain fields. Non-finite float fill values are canonicalized to the string forms the spec requires (`"NaN"`, `"Infinity"`, `"-Infinity"`), and `parse_dtype_v3` and `from_array` handle `bool`, `datetime64` and `timedelta64` data types, emitting the named-configuration form for the time dtypes. `GroupSpec` member names are validated against the Zarr V3 node-name rules (via `validate_node_name_v3`): besides the previously rejected empty string, `"/"`, `"."` and `".."`, a name composed of periods alone or starting with the reserved `"__"` prefix is now refused. This is breaking for specs that were constructible before but describe invalid metadata documents (for example an integer array with fill value `"NaN"`, a chunk shape whose rank disagrees with the shape, or a codec pipeline without an array -> bytes codec): constructing them now raises a `ValidationError` listing every problem.
